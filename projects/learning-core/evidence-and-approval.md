# Evidence and approval

Recommendations must remain explainable from approved inputs. These are reusable
review methods, not an approval record for a real family. Completed records stay
in explicitly approved private storage outside Git.

## Explain the recommendation

For each material plan statement, identify its input, attribution, date/version,
interpretation, uncertainty, and approval still needed. Use the smallest useful
map; link the owning record rather than duplicate private evidence.

| Plan section/version | Recommendation | Input reference and attribution | Interpretation or neutral structural default | Missing/counterevidence | Permission still needed |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

Keep parent report, approved learner voice, approved support context, neutral
template structure, and provisional assumption distinguishable. A default may
organize a plan; it cannot establish a learner-specific fact. Missing evidence
stays missing. Activity, completion, or a selected artifact does not prove mastery.
Several contextual signals can inform a cautious proposal, but no numerical
threshold validates a conclusion. Safety or withdrawn permission can require an
immediate pause without waiting for additional signals.

## Separate permissions

| Decision | What must be explicit |
| --- | --- |
| Discuss/classify | Purpose, relevant inputs, authority, and temporary handling. |
| Draft | Exact preparation scope and approved inputs; Ready alone is insufficient. |
| Use | Reviewed plan version, activities, resource limits, and pending exclusions. |
| Child-facing language | Exact prompts and delivery scope; learner may skip or stop. |
| Save | Categories/content, approved private destination, access, and retention/deletion choice. |
| Share | Exact content, recipient/destination, and purpose; saving is not sharing. |

An approval applies only to what the deciding human reviewed and authorized.
It does not establish educational suitability, effectiveness, clinical findings,
or compliance. Silence and general enthusiasm do not resolve missing permission.
No external communication is authorized by writing a review packet.

## Reconcile a parent change

1. Identify the reviewed version and exact change, including withdrawn permission.
2. Mark affected use pending or paused; do not keep declined elements active.
3. Revise every affected plan section, evidence rule, resource limit, and profile
   statement. Retain the prior version's disposition within approved retention.
4. Show the revised version and remaining uncertainties to the deciding human.
   Obtain exact confirmation where the previous approval did not cover it.
5. Compare the plan against the approval record. Record the actual save result
   only if saving was authorized; a failed save is not a persisted replacement.

Use this blank comparison in a private copy when useful:

| Reviewed version | Requested change | Affected sections | Revised version | Approved scope | Pending/declined | Storage result if authorized |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

If the plan and approval disagree, affected use remains paused until reconciled.
Learner corrections or removal requests stop reuse of that content while the
guardian resolves handling; do not repeat removed sensitive content in an audit.
Parent/learner disagreement remains visible without forcing agreement.

record is insufficient when its statements lack evidence or exact approval.
