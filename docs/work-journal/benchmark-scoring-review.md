## Assessment

The benchmark can expose weaknesses, but its current scoring rules cannot support a general claim that either system has better judgment. Several scores reward properties of the sample or wording rather than the capability being claimed. The following corrections are review proposals, not adopted requirements.

| Measure | How an apparent gain could mislead | Proposed correction |
| --- | --- | --- |
| M1: Falsifiability | Rephrasing a repeated claim can evade template detection without improving testability. Larger corpora have more opportunities for duplication. The protocol requires a resolvable observable, but the baseline's recorded checklist omits that requirement. | Treat the existing score as a lexical screen. Blindly assess matched new forecasts for observable failure conditions; report repetition separately. |
| M2: Loop closure | A fresh system starts with little backlog. Closing records prematurely could improve its count without resolving anything. The protocol includes median resolution latency, but the baseline reports overdue count and maximum delay, not that median. | Compare equally aged commitments with comparable evidence availability. Score whether dispositions are justified, alongside timeliness. |
| M3: Governance overhead | One brief per system cannot establish a stable cost difference. More expensive but better does not establish that the improvement warrants its cost. | Use repeated matched tasks, a predefined quality rubric, and an explicit acceptable cost-quality tradeoff. Retain blind judging. |
| M4: Ossification | Different labels can describe the same reasoning. If every row has a unique label, normalized entropy reaches its maximum regardless of analytical depth (for more than one row). Aggregate diversity cannot establish whether diversity declined over time. | Withdraw the strong hypothesis-falsified interpretation. Examine time windows and substantive mechanisms using stable categories. |
| M5: Independent routing | One eligible route supports a case study, not a general ranking. Withholding interpretations limits direct copying but does not remove shared source-selection effects. | Evaluate several independently reviewed cases and report shared inputs explicitly. A single result can reveal a specific error even though it cannot establish general superiority. |
| M6: Repeat-error rate | Remembering an old correction may help on a repeated problem while harming judgment when circumstances change. | Include both recurring errors and cases where the old lesson should be revised or rejected. |

Each row refers to the same-numbered entry in the protocol's `measures` array. M1 and M2 also compare `metric_definitions_frozen` and `results` in the baseline. These are design vulnerabilities and interpretation limits, not observed instances of gaming or descendant failure.

## Attribution and remaining obligation

The protocol varies accumulated history and governance together. Even a convincing difference would initially establish the effect of that combined arrangement; it would not identify which component helped or hindered. Shared curated evidence further bounds the comparison, as the protocol itself acknowledges under `controls.bounded_contamination`.

Recommendation: preserve the baseline as a historical diagnostic, then define prospective comparisons separately. Freeze task selection, scoring, exclusions, and interpretation rules before new results. The earlier read-only review also found a discrepancy between the baseline's recorded Git revision and ledger digest; that provenance issue remains unresolved and is not corrected by this scoring review.

Owning records remain the linked lineage protocol and baseline. This review assigns no new owner or deadline. Reconsider these recommendations before any comparative capability claim, after the source provenance and operational scoring definitions are resolved by the owning workflow. No comparative run or organizational outcome is established here.

## Proposed four-condition comparison

Added 2026-09-07 at the operator's request. This proposal separates memory availability from the additional governance workflow. It is not an adopted protocol or authorization to run an experiment.

| Condition | Prior memory available | Additional governance workflow |
| --- | --- | --- |
| 1 | No | No |
| 2 | Yes | No |
| 3 | No | Yes |
| 4 | Yes | Yes |

Without governance means removing only the workflow under evaluation, never safety, permissions, or mandatory repository controls. These are proposed experimental configurations, not changes to the live repositories.

Hold the model, task evidence, tools, output requirements, and resource ceilings constant. Define memory as an exact frozen set of prior records and governance as an exact set of procedures. Check that changing a procedure does not silently change the information available. Treat repository identity as context rather than the experimental variable.

- Compare 2 with 1 to ask whether memory helps without the additional workflow.
- Compare 3 with 1 to ask whether governance helps without prior memory.
- Compare 4 with 2 to ask whether governance improves how memory is used.
- Compare 4 with 3 to ask whether memory helps under governance.

An interaction means that the effect of one component depends on whether the other is present. For example, memory alone might introduce stale advice, governance alone might add little, and the combination might improve decisions because the workflow checks whether remembered lessons still apply. This is a hypothetical mechanism, not an observed result. Reporting only average effects could conceal it; report all four conditions and the conditional comparisons.

Judge output quality blindly across repeated matched tasks, including cases where memory is relevant, irrelevant, and misleading. Report quality and cost separately; do not combine them into one score without an explicit tradeoff.

This design tests use of an existing memory collection. It cannot establish whether governance produces better memories over time. That requires a later multi-session comparison starting from equivalent states and allowing records to develop. The task set, procedure definitions, scoring rubric, repetition count, and resource budget remain to be settled before execution. No efficacy or descendant-superiority claim follows from this design alone.
