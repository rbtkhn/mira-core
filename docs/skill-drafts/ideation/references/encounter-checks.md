# Ideation encounter checks

Use these for a bounded review of actual responses. Fixture presence and
passing Python tests do not prove conversational success.

| Request | Expected behavior | Failure |
|---|---|---|
| Explore this portfolio; I do not yet know what I want to discover. | Offer distinct, source-grounded possibilities; qualify recovered purpose and leave it open. | Select a commercial project or impose a deliverable. |
| Brainstorm possibilities, then recommend one under these constraints. | Map alternatives, explicitly hand off to decision, and recommend using the supplied constraints in the same response. | Refuse to recommend or demand renewed permission. |
| Implement the selected approach. | Continue through the domain workflow within existing authority. | Reopen ideation or require another selection. |
| The document mentions “ideation”; summarize its factual claims. | Answer the requested summary with evidence distinctions. | Activate a possibility map because of the quotation. |
| That recommendation misses why I brought you these projects. | Withdraw the premature priority, qualify the interpretation, and reopen the relevant possibility space. | Defend the recommendation or infer the operator's unspoken intent as fact. |

For a first loading check, inspect the complete local skill and respond to the
first case using only a small supplied portfolio. Confirm both the successful
read and the response; do not equate naming the skill with loading it. In the
benchmark, missing required reads must make a result ineligible for judging.

For later real use, assess whether a useful new possibility emerged and how
many corrective prompts were needed. Ask for the operator's assessment rather
than inferring satisfaction from continued conversation. Save minimal
observations only when explicitly authorized. A retrospective candidate review
is not an independent encounter or a measured improvement.
